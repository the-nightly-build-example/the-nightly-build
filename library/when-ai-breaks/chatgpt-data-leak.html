When AI Breaks

A cancelled request showed ChatGPT users other people's chat titles

The same bug also exposed some paying subscribers' card details, and it lived in an open-source library ChatGPT shared with much of the web.

9 min read2026-09-21

Why this matters

Most stories about ChatGPT going wrong are about the model: a made-up fact, a shift in how it behaves, an answer it should never have given. This one is not. For a few hours on 20 March 2023, ChatGPT showed some users other people's chat titles, and showed a slice of its paying subscribers pieces of other subscribers' payment details. The cause was an ordinary bug in the caching layer that every busy web service runs, and it drew Italy's privacy regulator into a case that ran for three years. By the end you will know how a cancelled request and a shared connection can hand one user another's data. You will also know exactly what OpenAI exposed and to how many, and what Italy's Garante did and did not order.

A stranger's chat titles in your sidebar

On Monday, 20 March 2023, some people who opened ChatGPT found conversations in their history that were not theirs. The sidebar down the left of the screen lists each past chat by a title drawn from its first message. For a stretch of that day, titles belonging to another active user showed up in the list instead.1

That was the visible part. Over the four days that followed, OpenAI traced the fault and disclosed that the same bug had also exposed payment details belonging to a slice of its paying subscribers.1 Neither problem was in the model that writes the answers. Both were in the layer that stores them.

How one request ends up reading another's answer

To keep ChatGPT responsive, OpenAI put a cache in front of its slower stores: a fast, in-memory holding area for data the server has looked up recently, so it does not have to fetch the same thing twice. The cache software is Redis, an open-source data store used across the industry.1

A service handling many requests at once does not open a new connection to Redis for each one. It keeps a set of open connections and lends a free one to each request, then takes it back when the request is done. That set is a connection pool.1 The trouble starts when a request is abandoned before it finishes, which happens constantly at scale: a user closes the tab, or the server gives up on a slow call and cancels it. Early on 20 March, a change OpenAI made caused a sudden spike in these cancellations.1 In OpenAI's account, "At 1 a.m. Pacific time on Monday, March 20, we inadvertently introduced a change to our server that caused a spike in Redis request cancellations. This created a small probability for each connection to return bad data."1

Here is how one cancellation returns bad data. The server takes a connection from the pool, sends its command to Redis, and waits to read the reply. The redis-py client that OpenAI used to talk to Redis holds commands it sends in one queue and replies it receives in another. If the request is cancelled in the gap after its command was sent but before its reply is read, the connection goes back into the pool still carrying that unread reply. The next request handed that same connection sends its own command, reads the first reply waiting for it, and gets the previous request's leftover data.12

The bug in OpenAI's words
"If a request is canceled after the request is pushed onto the incoming queue, but before the response popped from the outgoing queue, we see our bug: the connection thus becomes corrupted and the next response that's dequeued for an unrelated request can receive data left behind in the connection."1 OpenAI, March 20 ChatGPT outage report

A developer outside OpenAI had reported the same fault against redis-py three days before the incident, on 17 March. The report is titled "Off by 1" and traces the sequence step for step: after a cancelled command, "the following redis operation on the same connection will send the command, and then promptly continue to read the response from the previous, canceled command."2 Under the cancellation spike on 20 March, that off-by-one misdelivery happened often enough that one user's cached data surfaced in another's session.1

OpenAI took ChatGPT offline that day, patched its own systems, added checks that the data coming back from the cache belongs to the user who asked, and contributed a fix upstream.1 The redis-py maintainers merged it on 22 March: it shields a command from cancellation, so a request cancelled midway resets its connection instead of returning it to the pool dirty.3

One fix did not settle it. On 25 March the same reporter opened a follow-up, noting that the shielding covered only pipelined operations and that a single cancelled command outside a pipeline could still corrupt a pooled connection.4 Closing the fault took a second round.

Chat titles first, card details four days later

When ChatGPT went dark on 20 March, OpenAI did not say why. It put the outage down to a bug without naming the cause; the payment-data disclosure came only with the postmortem on 24 March.5 Sam Altman, OpenAI's chief executive, wrote at the time, "We feel awful about this."5

The reported scope grew as the investigation went. The first exposure was the chat titles, and the first message of a newly created conversation could also appear in another user's history if the two were active at the same moment.1 Deeper investigation found that the same bug had exposed payment-related information for 1.2% of the ChatGPT Plus subscribers who were active during a nine-hour window that morning, from 1 a.m. to 10 a.m. Pacific.1

That 1.2% is a ceiling, not a count. It measures how many active subscribers could have been shown another person's data in that window, not how many actually were; OpenAI said separately that the number of users whose data was actually seen by someone else was extremely low.1

What a subscriber might have seen depended on the route. Some were sent a subscription-confirmation email meant for a different user, carrying that user's credit card type and the last four digits of the number. Others, on the "Manage my subscription" page, saw another active subscriber's first and last name, email, payment address, card type, last four digits, and expiration date.1

OpenAI on the payment data
"it was possible for some users to see another active user's first and last name, email address, payment address, credit card type and the last four digits (only) of a credit card number, and credit card expiration date. Full credit card numbers were not exposed at any time."1 OpenAI, March 20 ChatGPT outage report

Italy blocks ChatGPT, on other grounds

Ten days later, ChatGPT stopped working in Italy. On 30 March 2023 the Garante, Italy's data-protection authority, ordered a provisional limitation on OpenAI's processing of the personal data of users in Italy, effective the moment OpenAI received it, using the GDPR's power to impose urgent measures.6

Much of the coverage said the regulator acted over the breach.7 The order's own text does not. It sets out four grounds, and the 20 March breach is not among them. OpenAI gave users no information notice and had no adequate legal basis for collecting personal data at scale to train the model. It processed inaccurate data because the model's outputs do not always match reality, and it ran no age check on a service its terms reserve for users 13 and older.6

Where the breach does appear is the Garante's press release the next day, as background to the action: it recorded that on 20 March ChatGPT had suffered "a data breach affecting ChatGPT users' conversations and information on payments by subscribers to the service."8 The breach shaped the episode without grounding the order.

The block held for about four weeks. The breach became a formal violation only later, in the Garante's decision of 2 November 2024, as a failure to notify the authority; the same decision fined OpenAI €15 million. That fine no longer stands: the Court of Rome annulled the decision in a judgment published 18 March 2026, upholding OpenAI's appeal.9

The same flaw, wherever state is cached

Nothing about this failure needed an AI. The bug lived in redis-py, an open-source client that many services use to reach Redis, and it was found by a developer with no connection to OpenAI.2 The ingredients are common: a cache holding per-user data, a pool of connections shared across requests, and requests that can be cancelled before they finish. Any busy service built that way can leak one user's data into another's session, whether it runs a chat window, an inbox, a bank account, or a store's checkout.12

An AI product sits on this same web plumbing, and a regulator will treat a leak from it as a data-protection event wherever in the stack it began.69 None of it needs a model to hand one person another's data.

The takeaway

The fault that exposed ChatGPT's users sat in front of the model, in the cache that keeps the service fast. A cancelled request left a shared connection holding one user's reply, and the next request read it as its own. The reply could be a chat title, or a subscriber's name and card details, and a privacy regulator followed on grounds of its own. Neither changes where the bug lived: in redis-py, an open-source library ChatGPT shared with much of the web. Its pattern, a per-user cache reached through pooled, cancellable connections, sits behind email, banking, and checkout alike. The thing to carry is that an AI product is a web service first. When such a service leaks one user's data to another, the cause is far more likely to be the plumbing than the model.
